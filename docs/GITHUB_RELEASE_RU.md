# Публикация и обновления через GitHub / Foundry

## Цель

Мастер должен устанавливать «Нити» через **Setup → Add-on Modules → Install Module → Manifest URL** и обновлять обычным механизмом Foundry. Не требовать ручной распаковки ZIP при следующих релизах.

## Предварительные условия

1. Узнай, какой аккаунт GitHub авторизован: `gh auth status` и `git remote -v`. **Не путать подключение GitHub к ChatGPT с авторизацией GitHub CLI в Codex**.
2. Предлагаемое имя нового репозитория: **`Jerrvik/niti-board`**, если это аккаунт пользователя и название свободно. Существующий `Jerrvik/right-to-speak` НЕ использовать.
3. Видимость: **public** для удобства установки мастером; проверить у пользователя перед необратимой публикацией, если Codex просит подтверждение. Не публиковать личные данные, учётные данные, токены, файлы миров или чужие портреты NPC без разрешения. Превью — абстрактная/собственная иллюстрация из проекта, а не чужие арты.
4. Опубликовать только код и документацию; рабочие скриншоты игрового мира мастера не выкладывать без разрешения.

## Внутренняя структура GitHub

```text
niti-board/
├── src/niti-board/
│   ├── module.json
│   ├── scripts/...
│   ├── styles/...
│   ├── ui/...
│   └── lang/...
├── docs/...
├── tests/...
├── README.md
└── .github/workflows/...  (при автоматизации релизов)
```

Манифест **в ZIP** должен лежать строго `niti-board/module.json`, не `src/niti-board/module.json` и не `niti-board/niti-board/module.json`.

## Три ссылки

- `url` — настоящий URL GitHub-репозитория.
- `manifest` — **постоянный публичный URL** на обновляемый `module.json`. Для BETA допустим `https://raw.githubusercontent.com/<owner>/<repo>/main/src/niti-board/module.json`, при условии, что он после каждого релиза указывает на текущий тестовый релиз.
- `download` — **версионный** URL на ZIP конкретного Release, например `https://github.com/<owner>/<repo>/releases/download/v0.1.0-beta.2/niti-board.zip`.

**Осторожно с `/releases/latest/`: GitHub может не считать prerelease «последним» обычным релизом.** Для BETA предпочтительнее стабильный `raw/main/.../module.json` либо специально настроенный стабильный адрес; не обещай автообновление без проверки.

## Порядок публикации

1. После работы/тестов зафиксировать новую BETA-версию **отличную от исходной `0.1.0-beta.1`** (предложение: `0.1.0-beta.2`).
2. Провести unit/статические проверки и собрать ZIP с единственной корневой папкой `niti-board`.
3. Подготовить release notes: функции, что проверено, что требует теста мастера, перечень известных проблем.
4. Выпустить tag/release через `gh` или GitHub UI; прикрепить архив.
5. Обновить `src/niti-board/module.json` в `main`: корректные `version`, `url`, `manifest`, `download`, `compatibility` с реальной степенью проверки.
6. Выполнить проверку прямых HTTPS-запросов к манифесту и ZIP, JSON парсинга, соответствия `version`/ссылок, содержимого ZIP. Проверить, что установки не требуют GitHub-авторизации.
7. Проверить (если Foundry доступна) установку через Manifest URL в чистый тестовый мир и следующее обновление. При недоступности честно указать «установка в UI не проверена».
8. В финальном отчёте сообщить **репозиторий, Manifest URL, Release URL, ZIP URL**. Не выдумывать их до фактической публикации.

## Желаемая автоматизация

Можно настроить workflow, который создаёт release-архив из `src/niti-board`, валидирует пути, заполняет manifest/download и прикрепляет файл к tag. Workflows должны иметь минимальные права (`contents: write` только там, где нужно). Учесть race condition: манифест в `main` должен ссылаться на **уже существующий** доступный ZIP.

## После первых отзывов мастера

Исправления — новым BETA-релизом и новой версией манифеста. Не перезаписывать молча существующий versioned ZIP — это мешает воспроизводимости тестирования.

Официальная документация: https://foundryvtt.com/article/module-development/ и https://foundryvtt.com/article/package-management/ .
