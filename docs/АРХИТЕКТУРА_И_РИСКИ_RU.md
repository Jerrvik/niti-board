# Архитектура и список рисков для обязательной ревизии

**Это не отчёт о найденных эксплуатируемых уязвимостях.** Ниже — конкретные места исходной BETA, подлежащие проверке/исправлению, прежде чем назвать многопользовательскую версию надёжной.

## Что уже есть в исходниках

- `src/niti-board/scripts/model.js`: `cleanNode`, `cleanEdge`, `cleanPatch`, `applyPatch`, `diffBoard`.
- `src/niti-board/scripts/module.js`: `world setting`, активный GM, `game.socket`, окно и iframe bridge, импорт актёров.
- `src/niti-board/ui/board.html`: редактор на JS/CSS, визуальные карточки/связи/стикеры/области.
- Оригинальный ZIP лежал в одноимённой папке Foundry. **Реального теста в сети из трёх клиентов не было.**

## А. Авторизация и синхронизация

A-01. В ранней BETA сокет `PROPOSE` принимает поле `authorId` **из самого сообщения**, а `APPLIED` слушается получателем без проверки подлинности отправителя. Широковещательный сокет Foundry не следует считать автоматически идентифицирующим инициатора. Проверить и не доверять заявленной роли/имени/GM из пользовательских данных. Изучить возможности V14 `User.query` / `CONFIG.queries` и поддерживаемых документированных событий, выбрать проверяемый путь. Официальная ссылка: https://foundryvtt.com/api/classes/foundry.documents.User.html . Если надёжная проверка ролей невозможна с избранной архитектурой, обозначить границы защиты, не утверждать серверную защищённость.

A-02. `PROPOSE` сейчас не содержит `opId`, `baseRevision`, адресного ACK. Произвольные задержки/дубли/смена GM могут приводить к устаревшему состоянию и расхождениям. Ввести централизованную последовательную запись, дедупликацию, ревизии, подтверждения и `resync`.

A-03. `post('PATCH')` отправляет локальному iframe только подтверждённые изменения, но локальные правки могут быть оптимистическими. Нужно явно определить rollback/rebase, когда GM отклонил изменение или поставил ограничение. Не допускать ложного статуса «сохранено».

A-04. Переподключение, смена ведущего, включение второй GM-сессии, поздний вход игрока, одновременная отправка 2 разных правок — обязательные сценарии.

## Б. Drag & drop и утечка скрытых NPC

B-01. Текущий iframe пытается получить `window.parent.foundry.applications.ux.TextEditor.getDragEventData(e)`; проверить реальную работу кросс-документного drag/drop в Foundry V14. Официальный API: https://foundryvtt.com/api/classes/foundry.applications.ux.TextEditor.html . Если iframe мешает, обработать drop у родителя или перейти на другой вариант UI.

B-02. После получения Actor UUID нельзя «подглядывать» в закрытый документ и раскрывать его через доску игроку. Игрок импортирует только актёров, которые ему действительно разрешены; если GM добавляет скрытого актёра на **публичную** доску, нужно явное предупреждение. Исходная проверка прав только на первом игроке недостаточна.

B-03. `actorUuid` в публичной карточке — тоже часть раскрываемых данных. Не публиковать скрытую игровую статистику/имена вне сознательного GM-действия. Двойной щелчок может открыть Actor только при наличии прав.

## В. Безопасность данных и изображения

C-01. Поле photo допускает URL и data URLs. Ограничить размеры и схемы URL, не позволять инъекции через HTML-атрибуты, не хранить огромные base64 изображения в world setting. При предпочтении Foundry FilePicker соблюдать текущий API.

C-02. Проверить вставку текста на доску: HTML-экранирование подписей/заметок, отсутствие `innerHTML` с сырым пользовательским вводом, обработка ссылок и title безопасным способом.

C-03. Блокировка карточки не должна быть только CSS/disabled. Обработка подтверждённого изменения на авторитетном клиенте должна применять правило, при этом защита от случайного удаления — не обещание защиты от умышленно модифицированного клиента.

C-04. Импорт JSON и копии карточек: валидация формата, уникальность ID, ссылки только на реальные узлы, лимиты, подтверждение замены. Не загрязнять глобальные переменные и чужие модули.

## Г. Работа с данными

D-01. Объём данных world setting ограничен практическими соображениями. Рекомендуется лимит пользовательских фото (сжатие/внешняя папка внутри Data), лимит board JSON и отчёт при превышении.

D-02. `revision` не должен переустанавливаться по порядку прихода сокетов. Актуальный state нужно можно запросить полностью.

D-03. Не перезаписывать сохранённую доску демо-данными при первом входе / сбое передачи состояния.

D-04. Экспорт JSON — страховка перед первой установкой и обновлением. Любая миграция версии данных — обратимо/с бэкапом.

## Е. Приоритеты для Codex

**P0 до публикации тестовой сборки:** drag/drop, сохранение, multi-client, базовая авторизация сообщений, отсутствие XSS/скрытых Actor leaks, корректная установка.

**P1 обязательно для удобной BETA:** ACK/revision/resync, ошибочные операции, читабельное редактирование нескольких связей, undo без повреждения чужих правок, backup/export/import.

**P2 позже:** несколько досок, скрытые слои, сложное автоматическое выстраивание, AI, персонажные справочники.
